Как устроена фича «Добавить карту»

Построчный разбор всего, что было написано для фичи card: зачем каждый файл существует, что означает каждая конструкция языка и почему выбран именно такой вариант, а не другой. Код во всех примерах читается напрямую из репозитория — если ты что-то поменяешь в файле, этот документ можно перегенерировать, и он снова будет один в один соответствовать коду.

Как этим пользоваться

  1. Слева — список всех файлов по слоям (Domain → Data → Presentation), в порядке, в котором их имеет смысл читать первый раз.
  2. Сначала загляни в «Мини-справочник по синтаксису» — там разобраны конструкции Dart, которые повторяются почти в каждом файле (сокращённый синтаксис .foo, каскады, records), чтобы не объяснять их каждый раз заново.
  3. В каждом файле код показан целиком с номерами строк; под ним — пронумерованные карточки с разбором конкретных строк (номер карточки = подсвеченный участок кода того же цвета).
  4. У каждой карточки три поля: что это (термин/конструкция), как работает вообще (общее объяснение языка/фреймворка) и почему так у нас (конкретное решение в этом коде).

Обзор

Мини-справочник по синтаксису

Эти конструкции встречаются в коде фичи снова и снова. Разобраны один раз здесь, дальше по тексту на них есть ссылки.

final class

Что это
Модификатор класса в Dart 3. final class нельзя ни унаследовать (extends), ни реализовать (implements) за пределами своего файла/библиотеки. Обычный class разрешает и то, и другое где угодно.

Мы вешаем его почти на каждый класс фичи (CardEntity, CardModel, CardCubit, все виджеты) — это способ сказать «это конкретная реализация, а не точка расширения». Если кому-то понадобится сделать альтернативную реализацию — для этого есть abstract interface class (следующий пункт), а не наследование от final class.

abstract interface class

Что это
Класс без реализации, который существует только как контракт. abstract — нельзя создать экземпляр напрямую (CardRepository() — ошибка). interface — можно только implements, но не extends (то есть реализующий класс обязан переопределить вообще все методы, ничего не наследуя).

Ровно так объявлены CardRepository и CardLocalDataSource. Domain-слой знает только про интерфейс CardRepository, а про то, что за ним стоит SharedPreferences — не знает вообще. Это и есть Dependency Inversion из Clean Architecture: домен диктует контракт, data — подчиняется ему.

Синтаксис-сокращение .foo

Что это
Относительно новая возможность Dart: когда компилятор точно знает ожидаемый тип по контексту (тип параметра, тип поля, возврат функции), можно опустить имя типа и написать .value вместо ТипName.value.

По всему коду фичи это встречается постоянно: status: .loading вместо status: Status.loading (параметр типизирован как Status), borderRadius: .circular(24) вместо BorderRadius.circular(24), DateTime now = .now(), selection: .collapsed(...). Это чисто про читаемость — поведение абсолютно то же самое, что при полном имени типа.

Каскады ..

Что это
Каскадный оператор вызывает несколько методов/сеттеров подряд на одном и том же объекте, не повторяя имя переменной и не создавая промежуточных копий.

cardNumberController..removeListener(_onFieldChanged)..dispose(); — обе операции идут на одном контроллере. Или в CustomPainter: canvas..save()..clipRRect(window)..drawRect(lineRect, paint)..restore(); — четыре вызова на одном canvas одной цепочкой.

Records (кортежи) и typedef

Что это
Records — лёгкий тип-кортеж без объявления класса: (String, int) или именованный ({String cardNumber, String expiry}). Сравниваются по значению полей, immutable. typedef просто даёт короткое имя длинному типу.

typedef CardScanResult = ({String cardNumber, String expiry}); — вместо отдельного класса ScanResult с конструктором/полями/equals для передачи двух строк через Navigator.pop. Дешевле, чем городить класс ради двух полей.

Pattern matching: switch-выражение и if (x case ...)

Что это
switch в Dart 3 — это не только оператор, но и выражение, возвращающее значение, с проверкой исчерпанности всех вариантов enum на этапе компиляции. if (value case Pattern p) — «мягкий каст с проверкой», привязывает переменную только если совпадение есть.

В NfcReadDialogWidget один switch (widget.status) сразу возвращает record из четырёх полей (заголовок/подзаголовок/иконка/цвет) для каждого статуса. В CardPreviewWidget: if (brandLabel case final String label) — рисуем бейдж бренда, только если строка не null, без отдельного if (brandLabel != null) { final label = brandLabel!; ... }.

Null-safety: ?, ??, !, ?.

Что это
String? — тип, допускающий null. ?. — вызов метода/геттера, который вернёт null, если сам объект null, не упав с ошибкой. ?? — «если слева null, взять правое значение». ! — «я знаю, что тут не null, доверься мне» (упадёт в рантайме, если ошибся).

formKey.currentState?.validate() ?? false — если форма ещё не построена (currentState == null), считаем валидацию проваленной, а не падаем. state.errorMessage ?? context.l10n.cardAddError — на случай, если исключение почему-то не заполнило текст ошибки.

Extension methods

Что это
Способ «пришить» новые методы к чужому типу (даже String из dart:core) без наследования — просто extension Name on String { ... }.

.onlyDigits, .orDefault(), .isNotBlank — это всё extension-методы из lib/src/common/extensions/string_ext.dart, которые фича переиспользует. То же с context.color, context.l10n, context.hideKeyboard() — extension-методы на BuildContext из context_ext.dart.

async / await / Future<T>

Что это
Future<T> — «значение типа T появится позже» (аналог Promise). async помечает функцию, которая может «приостанавливаться» на await, не блокируя UI-поток. await — «жди результат, но не мешай остальному приложению крутиться».

Вся цепочка сохранения карты — Future: UI → Cubit (async, await _addCardUseCase(card)) → UseCase → Repository (async, await _localDataSource.getCards()) → DataSource → диск. Ни один из этих await не морозит интерфейс.

Дженерики <T>

Что это
Параметризация типа: List<CardModel> — список именно моделей карт, а не «список чего угодно», с проверкой на этапе компиляции.

sl.registerLazySingleton<CardRepository>(...) — GetIt регистрирует фабрику именно под тип CardRepository, и потом sl<CardRepository>() вернёт объект именно этого типа без ручного каста.

Спред-оператор ...

Что это
Разворачивает элементы одной коллекции внутрь другой прямо в литерале: [...cards, card] — новый список из всех старых карт плюс одна новая, без ручного List.from(cards)..add(card).

Используется в CardLocalDataSourceImpl.addCard: читаем сохранённые карты, «расширяем» список новой картой и целиком перезаписываем JSON.

Геттеры get

Что это
Свойство, которое вычисляется по требованию при каждом обращении, а не хранится как поле. Синтаксически выглядит как переменная (widget.isFormValid), а не как вызов метода.

bool get isFormValid => ... в AddCardState каждый раз заново считает длину введённых цифр — состояние не кэшируется, значит не рассинхронизируется с тем, что реально в контроллерах.

StatelessWidget vs StatefulWidget

Что это
StatelessWidget — «нарисуй один раз по входным параметрам, сам ничего не помнишь». StatefulWidget — виджет, у которого есть отдельный State-объект, переживающий перерисовки и хранящий изменяемые данные (текст поля, позицию анимации).

Экраны фичи (AddCardScreen, CardScannerScreen) — StatefulWidget, потому что им нужны контроллеры/фокус/анимации, которые обязаны жить дольше одного build(). Мелкие декоративные штуки (CardActionButtonWidget, ScannerResultWidget) — StatelessWidget, им нечего запоминать.

BuildContext

Что это
«Адрес» виджета в дереве прямо сейчас: через него ищут ближайший Theme, ближайший Cubit, ближайшую локализацию — вверх по дереву предков.

context.color.primary, context.l10n.cardAddTitle, context.read<CardCubit>() — все они ищут по дереву вверх от текущего виджета: тему, приложенную в MaterialApp, локализацию, приложенную там же, кубит, приложенный через BlocProvider на роуте.

Cubit / BLoC

Что это
Cubit — упрощённый BLoC: объект, который хранит один state и умеет заменить его на новый через emit(newState). Все виджеты, подписанные на этот Cubit (BlocBuilder/BlocConsumer), перерисовываются автоматически при каждом emit.

CardCubit хранит CardCubitState{status, card, errorMessage}. Экран не трогает данные напрямую — он просит кубит addCard(...) и реагирует на смену state.status.

CustomPainter / Canvas

Что это
Способ рисовать произвольную графику вручную — линии, дуги, заливки — вместо готовых виджетов, когда нужной фигуры (рамка со скруглёнными уголками, бегущая линия) в стандартном наборе нет.

_ScannerOverlayPainter рисует затемнение с прозрачным окном под форму карты через Path.combine(PathOperation.difference, ...), уголки — вручную построенным Path, бегущую линию — градиентной заливкой прямоугольника, который двигается по значению анимации.

AnimationController / SingleTickerProviderStateMixin

Что это
AnimationController — число от 0 до 1, которое меняется во времени по расписанию (кадр за кадром). vsync синхронизирует эти кадры с частотой обновления экрана — без него виджет мог бы анимироваться даже когда невидим, впустую тратя батарею. SingleTickerProviderStateMixin — миксин, который и даёт этот vsync.

В CardScannerState — бегущая линия сканера (_scanController, туда-обратно), в NfcReadDialogWidget — расходящиеся круги вокруг иконки NFC (_pulseController, по кругу).

Dependency Injection / GetIt

Что это
Вместо того чтобы класс сам создавал себе зависимости (CardRepositoryImpl() внутри кубита), их «впрыскивают» снаружи через конструктор. GetIt — сервис-локатор: реестр «по этому типу дай мне готовый объект», без ручной передачи через десяток конструкторов.

sl<CardRepository>() в _initCard() достаёт из реестра уже собранный CardRepositoryImpl, которому GetIt сам подставил CardLocalDataSource, а тому — LocalSource.

Переопределение ==

DartТестирование
Что это
Оператор сравнения по значению: два CardEntity с одинаковыми panNumber/cardExpire теперь считаются равными.
Как работает вообще
По умолчанию Dart сравнивает объекты по ссылке (identical) — два отдельно созданных объекта с одинаковыми полями не равны, пока не переопределён ==. identical(this, other) — быстрый путь (это буквально один и тот же объект в памяти). runtimeType == other.runtimeType — защита от случайного сравнения с объектом другого (под)класса.
Почему так у нас
Без этого не заработали бы тесты: bloc_test сверяет ожидаемые состояния кубита по значению, а mocktail's verify(() => repo.addCard(card)) сравнивает переданный в мок аргумент так же — по ==, а не по ссылке.

Как работает вообще

Регулярные выражения

Алгоритм
Что это
Три static final RegExp: номер, срок и «всё, что не цифра».
Как работает вообще
(?<!\d) и (?!\d) — это lookbehind и lookahead, «слева не цифра» и «справа не цифра». Они не попадают в найденную подстроку, а только ограничивают её. (?:\d[ \-]{0,2}){16} — «шестнадцать раз: цифра, за ней до двух пробелов или дефисов».

_findPan: сбор кандидатов и приоритет

АлгоритмДомен
Что это

_findExpiry: почему берётся максимум

АлгоритмДомен
Что это

Алгоритм Луна

Алгоритм
Что это
Классическая проверка контрольной суммы номера карты.
Как работает вообще
Идём справа налево; каждую вторую цифру удваиваем, и если получилось больше 9 — вычитаем 9 (это то же самое, что сложить цифры результата: 14 → 1+4 = 5 = 14−9). Почему так у нас
Этот алгоритм ловит опечатки в одной цифре и перестановку соседних — то есть ровно те ошибки, которые чаще всего делает OCR, спутав 8 и 3 или 1 и 7. Для сканера это главный фильтр качества: он отличает «прочитал номер» от «прочитал номер с ошибкой».

Без них кубит нельзя было бы даже создать в тестовой среде: availableCameras() полез бы в нативный канал, которого нет.

Внедрённые часы

RecognizeCardUseCase принимает DateTime Function() now. Тест передаёт () => DateTime(2026, 9, 5), и проверки окна дат прибиты к фиксированной точке.

С DateTime.now() внутри тест «дата 05/10 слишком старая» протух бы сам собой через несколько лет — и упал бы у того, кто откроет проект в 2036-м.

Мокается интерфейс, а не final class

В Dart final class нельзя реализовать вне своей библиотеки — значит, замокать use case через mocktail невозможно. И не нужно: тест кубита создаёт настоящие use case поверх мока репозитория.

Репозитории объявлены как abstract interface class именно затем, чтобы их можно было подменить. Граница подмены совпадает с границей слоя.

Что осталось непокрытым — и почему это честно сказать на защите

  1. Виджет-тестов на сам экран сканера нет: он почти целиком состоит из CameraPreview, который без устройства не отрисовать.
  2. Качество распознавания на реальной карте тестами не измеряется — проверяется логика разбора уже распознанного текста, а не работа ML Kit.
  3. Ошибка вёрстки, которую нашли при сборке (вложенный Column без mainAxisSize: .min), не ловится ни анализатором, ни юнит-тестом — только запуском экрана.
Итог

Почему именно так

Почему хранение — через LocalSource.stringEntry, а не новый пакет

local_source — отдельный workspace-пакет с фиксированным набором миксинов (settings/session/user). Вместо того чтобы туда лезть и добавлять миксин под карты, датасорс просто переиспользует уже публичный низкоуровневый метод stringEntry(key: ...) — он экспортирован из пакета специально для таких случаев. Один JSON-список карт под одним ключом.

Почему в CardCubitState нет Action-энума

В проекте это паттерн для кубитов с несколькими операциями (у AuthCubit есть login/logout, и action нужен, чтобы UI понимал, какую из них слушать). У CardCubit сейчас одна операция — добавить карту, — поэтому схема проще: {status, card, errorMessage}, как у HomeCubit/ProfileCubit. А вот в той же фиче CardScannerCubit энум CardScannerAction уже есть — там операций четыре, и экрану надо отличать отказ камеры от отказа в разрешении. Один и тот же принцип даёт разный ответ для двух кубитов рядом.

Почему камера живёт в кубите, а не в data/

Соблазн был: камера — «внешний ресурс», значит ей место в датасорсе. Но CameraController — это ещё и UI-объект: виджет CameraPreview(controller) требует именно его, живьём. Спрятав контроллер в data-слой, пришлось бы протаскивать его обратно наверх через все слои — и слой перестал бы что-либо изолировать. Поэтому граница проведена в другом месте: в кубите остаётся железо (открыть, закрыть, поток кадров), а в data ушло распознавание (ML Kit) и разрешения. Домена ни то, ни другое не касается.

Зачем нужен CameraFrameEntity, если есть CameraImage

Ровно ради одной строки в правилах проекта: domain/ — чистый Dart, без сторонних SDK. Если бы RecognizeCardUseCase принимал CameraImage из пакета camera, домен зависел бы от плагина, а тесты разбора номера требовали бы камеру. Промежуточная сущность из байтов и чисел стоит тридцати семи строк — и за счёт неё 16 тестов парсера гоняются на ноутбуке за доли секунды.

Почему проверка Луна не обязательна

Классический совет — «принимай номер, только если сходится контрольная сумма». Для Uzcard и Humo это не работает: их PAN не всегда удовлетворяет алгоритму Луна, и жёсткая проверка отсекла бы часть настоящих местных карт. Поэтому сделано двухуровнево: сначала ищется кандидат с корректной контрольной суммой, и только если такого нет — принимается номер с локальным BIN (8600/9860). Сильное доказательство побеждает слабое, но слабое лучше, чем отказ.

Почему кадры прореживаются, а не обрабатываются все

Камера отдаёт ~30 кадров в секунду, одно распознавание занимает десятки миллисекунд. Без ограничения очередь росла бы быстрее, чем разгребается: телефон греется, превью тормозит, а пользы ноль — за 33 мс картинка почти не меняется. Два предохранителя: интервал 350 мс и флаг «кадр уже в работе». Плюс поток останавливается совсем, как только распознаны оба поля.

Почему BlocProvider сканера стоит на его собственном роуте

Это решение про освобождение камеры. go_router снимает роут при pop — и ровно в этот момент BlocProvider зовёт close() у кубита, а тот закрывает камеру и распознаватель ML Kit. Подними провайдер на уровень /add-card — и камера продолжала бы работать всё время, пока пользователь заполняет форму.

Почему в кубите два catch подряд

on DuplicateCardException catch (e) и следом обычный catch (e) делают сейчас одно и то же — оба просто кладут e.toString() в errorMessage. Но типизированный catch — это место, куда позже подставится реакция именно на дубликат (например, отдельный текст с предложением «открыть уже добавленную карту»), без риска случайно поймать вообще любое исключение под этим же условием. Паттерн скопирован с AuthCubit.

Почему у CardEntity и CardCubitState есть ==/hashCode

Без переопределённого == два объекта с одинаковыми полями всё равно не равны — сравнение идёт по ссылке (identical). Это не только теоретическая правильность: без этого не работает сравнение состояний в тестах кубита и сравнение аргументов в моках — оба инструмента сверяют объекты «по значению».
